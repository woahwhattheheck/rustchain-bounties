## Finding 1 — `MAX_PER_RUN=40` is documented as an aggregate RTC ceiling but implemented as a claim-count ceiling

`bounty_payout.py` documents `MAX_PER_RUN aggregate cap (default 40) — hard stop per run`, but current main sets:

```python
MAX_CLAIM_RTC=float(os.environ.get("MAX_CLAIM_RTC","25")); MAXRUN=int(os.environ.get("MAX_PER_RUN","40"))
...
paid=0; total=0.0
for i in issues:
    if paid>=MAXRUN:
        break
...
if ok:
    paid+=1
    total+=amount
```

The guard compares the number of successful claims to 40, not the RTC total.

Concrete green-but-wrong path: two valid docstring claims may each carry a trusted 25 RTC amount marker (the separate per-claim ceiling). The first succeeds with `paid=1,total=25`; the second still passes `paid < 40`, succeeds, and leaves `paid=2,total=50`. The run is green and explicitly prints 50 RTC paid despite the documented 40-RTC aggregate ceiling. In the worst permitted shape, 40 × 25 RTC = 1,000 RTC can pass before the claim-count guard fires.

Expected: bind the ceiling to `total + amount`, with any separate claim-count safety bound named and enforced independently.

## Finding 2 — the rolling seven-day docstring cap filters by claim creation time, not grant time

`docstring_gate.py::docstring_rtc_this_week()` says it measures RTC granted in seven days, but searches:

```python
since = (datetime.datetime.now(datetime.timezone.utc)
         - datetime.timedelta(days=7)).strftime("%Y-%m-%d")
q = (f"repo:{REPO} is:issue author:{author} label:docstring-verified "
     f"created:>{since}")
```

It then sums the gate's `rtc-payout-amount` markers from those issues.

Concrete green-but-wrong path: a claim opened ten days ago waits for its PR to merge, is verified today for 25 RTC, and receives the trusted amount marker today. A later claim adjudicated today excludes that 25 RTC because the issue was created ten days ago. `already` is understated, so the later claim can be approved through the intended 40 RTC rolling-week ceiling even though every API call succeeds. Old-create/new-verification is an expected lifecycle because the gate explicitly holds unmerged claims for later re-check.

Expected: determine the rolling window from the trusted gate-verification/payment event timestamp, not issue creation time. A practical implementation can discover recently updated verified claims and then count only trusted amount-marker comments created inside the seven-day window.

## Finding 3 — review backfill silently caps authoritative discovery at 1,000 while the repo currently has 1,048 open issues

Current `pr_review_gate_backfill.py` discovers:

```python
["gh", "issue", "list", "-R", REPO, "--state", "open",
 "--limit", "1000", "--json", "number,title,labels"]
```

Only after that capped list is returned does it classify `never`/`stranded` and compute the visible remainder. The safety comments say a missed webhook should cost hours rather than forever, and that bounds must report the remainder; however omitted discovery rows are not part of `total`, so they cannot appear in the remainder notice.

Live public GitHub state during this audit reports `total_count: 1048` for `repo:Scottcjn/rustchain-bounties is:issue is:open`, so the fixed 1,000-item enumeration ceiling is active now. There are also live old open review claims in exactly the retry class; e.g. #8733 is open with both `needs-human` and `gate-processed`, created 2026-05-06 and updated 2026-09-13. The backfill explicitly classifies `needs-human` review claims as stranded **if discovery reaches them**.

This is the same failure family as the historical 400-item payout sweep described in #16471, now in the adjudication recovery layer.

Expected: paginate the REST issues collection to exhaustion and only then apply `MAX_PER_RUN` to adjudication work. Any enumeration failure/unexpected shape should fail red.

### Patch included on this branch

The accompanying patch replaces the fixed `gh issue list --limit 1000` discovery call with `gh api --paginate --slurp` over `/repos/<repo>/issues?state=open&per_page=100`, validates and flattens every page, explicitly excludes pull-request objects (REST `/issues` includes them), and keeps `MAX_PER_RUN` exclusively as an adjudication bound. Regression coverage exercises multi-page flattening, PR exclusion, malformed/mixed response failure, and existing classification behavior.
